LLMs propose, verifiers check: our work on LLMs and formal verification

Created on October 30, 2026

2026   ·   formal-verification   llms   esbmc   ·   research

A language model can produce a loop invariant, a function contract or a patch in seconds. It cannot tell you whether any of those things is actually correct. A model checker can. Unwinding assertions confirm that a loop bound covers every iteration, k-induction proves properties of unbounded executions, and ranking functions prove that loops terminate. The checker still needs a property to verify, and for deep/nested loops and large codebases the proof often depends on an invariant or contract that no one has written. Each side fills a gap in the other.

Since 2023 our Systems and Software Security (S3) group at the University of Manchester and our collaborators have looked at what happens when the two share a loop. Much of this work has used ESBMC, the SMT-based model checker that we develop. ESBMC combines abstract interpretation through interval analysis, model checking through bounded model checking and k-induction, deductive verification through function contracts [1], and SMT solving. A recent survey looks at how it has become the verification backend for LLM-based tools [2].

Our work since 2023

1. How safe is LLM-generated code?

We started off by asking how often LLM-written code is unsafe, and used ESBMC to find out. More than half of the C programs that GPT-3.5-turbo wrote for our FormAI dataset had at least one vulnerability [3], and a follow-up across nine LLMs found at least 62% [4].

Model checking every completion is too slow for an IDE, so we used these verifier-checked labels to train SecureFalcon, a small classifier that flags vulnerable code instantly on a CPU [5].

Formal tools have blind spots too. On the CASTLE benchmark, ESBMC raised the fewest false alarms but missed vulnerabilities outside the properties it checks, such as weak cryptography, while LLMs got worse as programs grew [6]. A survey chapter covers the wider area [7].

2. Counterexample-guided repair and generation

When ESBMC finds a violation, it returns a counterexample: a concrete input and the execution trace that leads to the failing check. That makes it a precise bug report, so we pass it back to an LLM. ESBMC-AI (posted May 2023) takes the source code, the counterexample and the stack trace and feeds it to an LLM, and ESBMC then re-verifies the patch. It was evaluated on 50k FormAI programs [8]. ESBMC-AI has since been succeeded by Entoli, an open-source agent with formal-verification-based workflows. The same loop also works for neural-network code: ESBMC checked about 81k mutated neural-network programs, and an LLM repaired the bugs that ESBMC found [9]. VeriExploit runs it in reverse: you start with a Solidity counterexample and an LLM generates an attacker contract which re-triggers the bug. That contract is then validated by a model checker and is able to reproduce 85.60% of the bugs in our benchmark [10]. For legacy C code, UnitTenX turns ESBMC counterexamples into readable unit tests [11].

3. LLMs supply what the verifier is missing

Here the LLM writes out the invariants and contracts that a proof needs, and a sound tool then decides whether to believe them.

  • Invariants. ESBMC ibmc replaces each loop with an LLM-generated invariant which a theorem prover then checks. It was able to verify programs that SeaHorn and VeriAbs were unable to verify and went on to receive an ACM SIGSOFT Distinguished Paper Award [12]. VerIbmc takes the same approach using open-weight models on a single local machine and solves 431 of the 499 problems in its best configuration, GPT-OSS-120B [13].
  • Contracts. ConVer takes a top-level property and synthesizes function contracts from it, refining them in a CEGAR-CEGIS loop and achieving 82-96% success on 45 Frama-C programs, the easiest of its four benchmark suites, and as low as 33% on the harder ones [14]. For regression verification, partial LLM-inferred contracts produced zero false equivalence proofs on EqBench-C [15].
  • Agents. Agentic model checking is based on the principle of ‘agents propose, solvers verify’ where the agent works out the specifications and plans the run, with all soundness-critical decisions remaining with the bounded model checker (CBMC and Kani). On mature, heavily fuzzed software it found 68 source-audited defects across 11 projects [16].

4. From prose and other languages to checkable models

SpecVerify uses Claude 3.5 Sonnet in conjunction with ESBMC to derive properties from requirements. On nine of Lockheed Martin’s cyber-physical systems it achieved the same result as NASA’s CoCoSim but with fewer false positives [17]. The models still occasionally misread the specifications, so human review remained necessary. INVAR takes a document (e.g. the USB 2.0 or CXL 4.0 specification) and extracts a transition system from it, which it then checks with NuSMV and reports any missing evidence as a named gap rather than a vacuous pass [18]. With NASA JPL we use an LLM to translate Python into C for ESBMC. The paper makes the caveat that as the translation doesn’t prove equivalence the outcome is only bug finding and not verification [19]; the agent and benchmark are both public.

5. Reviews of the field

Two reviews place this work in a wider context: one which provides a taxonomy of the generative transformations and their recurring patterns in over 100 LLM-based proposals for software verification and falsification [20], and one which is a systematic review of 38 studies on LLM agents, which identifies specification as the bottleneck rather than checking [21].

The papers all follow the same pattern of division of labor. The LLM does the semantic guessing (what a loop maintains, what a function assumes, what a requirement means). A sound tool provides the guarantee. Over time the LLM has been trusted to do more and more. It started off just being measured, then it was used to repair code under a whole-program verifier, then it was used to write parts of the proof and in the agentic model checking work it’s used to plan the entire run. Invariants and contracts are proved before they are used, so a wrong guess is rejected. Assumptions about the environment are different: they are trusted, not checked. If an LLM writes an assumption that rules out every input reaching an assertion, the verifier reports success vacuously. That is why our pipelines check the evidence itself: each LLM-written harness has a seeded-bug twin that must fail, and INVAR reports missing evidence as a gap rather than a pass. A number of the papers are also direct extensions of one another. FormAI provided the evaluation set for ESBMC-AI and the training data for SecureFalcon. VerIbmc builds on the ibmc invariant work.

The negative results are just as important as the positive ones. CASTLE shows us the limitations of the formal tools. SpecVerify shows that the prose still requires a human to read it. The Python work is very clear that, without a verified translation, the method can find bugs but cannot prove the code correct.

Lessons learned

Benchmarks come with an answer key; production code does not. In recent work an LLM agent drafted verification harnesses for codebases such as the AWS SDK for C++, NVIDIA OpenSMA firmware and vLLM, ESBMC checked them, and maintainers merged 18 fixes upstream, including fixes for two CVEs in the AWS SDK for C++. Five lessons from that work and the papers above, presented at FATTW 2026:

  1. Zero false positives beats a higher proof rate. Developers stop trusting a tool that raises false alarms.
  2. Maintainers fix what arrives with a concrete input. The counterexample is the bug report.
  3. The generator’s quality still propagates. With GPT-4o instead of Claude 3.5 Sonnet, SpecVerify produced 8 false positives instead of 0.
  4. We do not win every benchmark. SeaHorn proves more programs than ibmc, and CoCoSim matches SpecVerify; portfolios beat single tools.
  5. Verifiers have traps too. Zero verification conditions, disabled unwinding assertions and contracts that silently check nothing all look like success, so the evidence itself needs checking.

What comes next

The talk closes with three challenges that neither academia nor industry can solve alone:

  • Verification at generation speed. Agents generate code in seconds, while industrial proofs take minutes to hours, so checking must reuse earlier proofs incrementally.
  • Guarantees for agent workflows. Verifying each agent is not enough to verify the workflow they form; we need compositional contracts between agents.
  • Evidence we can trust. DO-178C already accepts formal evidence through DO-333, which raises the question of who checks the checker. Witnesses and validators are part of the answer.

Underneath all three sits the problem that every line of work above runs into: how do we validate a specification an LLM has derived from natural language before anything is proved against it?
